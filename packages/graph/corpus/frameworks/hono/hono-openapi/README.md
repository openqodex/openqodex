The layout of the customer's Hono service: OpenAPI routes defined as data with `createRoute` in one file (imported under another name, `defineRoute`), registered in another file with `router.openapi(route, handler)` inside a factory function that builds and returns a router, and mounted from a third file with `app.route(prefix, withAuth(createUsersRouter(...), requireAuth))`, where `withAuth` makes a new router, adds the middleware and mounts the router it is given at `/`. A settings router mounts the same factory again under its own prefix. Paths are written OpenAPI style (`/{user_id}`) and served by Hono as `/:user_id`. It also plants: zod schemas with their own `.openapi("User")` call, which are no routes; a route whose path is computed; a handler made by a call; a wrapper that returns a fresh router and never mounts the one it is given; and a mount of a function that is defined nowhere. A reader that only knew `app.get` would list one route; one that guessed would list the users routes under `/api/v1/other`, where they are not served.
